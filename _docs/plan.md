# 食材库存与菜谱 Agent｜产品范围

> 产品阶段：MVP｜文档版本：1.0｜决策状态：范围冻结。本文只保留最终选择；被后续决定推翻的早期方案已删除。下文“V1”均指 MVP 之后的产品阶段，不是本文档版本。

## 1. 产品定位

微信小程序，核心是 **食材管理 + 库存约束下的菜谱推荐**。

产品围绕动态库存回答三个问题：

1. 家里现在有什么、哪些应优先使用；
2. 基于现有库存，下一顿最适合做什么、还缺什么；
3. 用户提出口味、时间、厨具、饮食模式等要求后，AI 如何调整方案并保持库存与补买清单一致。

核心价值是减少食材浪费、降低“今天吃什么”的决策成本、尽量少补买。产品不是摄入或营养追踪工具；营养只以粗粒度标签参与推荐。

## 2. 目标用户

- MVP：单用户、以一人做饭为主要场景。
- 默认 1 人份；用户可设置长期默认人数，也可在每次推荐时临时改为 2 人或 3 人以上。
- 人数变化后，菜谱用量、库存占用、预留量和补买量自动重算。
- 使用微信身份登录，库存、收藏、偏好、待制作菜谱等保存在云端并跨设备同步。
- 数据模型预留多人家庭能力，但 MVP 不提供共享库存、多成员偏好或成员级消耗记录。

## 3. 信息架构与导航

一级导航固定为 4 个 Tab：

1. **首页**：提醒与下一步决策，不放库存概览。
2. **库存**：完整食材库存与常备品管理。
3. **AI**：统一 Agent 对话与快捷任务。
4. **我的**：收藏、已制作历史、饮食偏好/模式、厨具设置。

菜谱详情、临期详情、购物清单、待制作列表均为二级页面，不占一级 Tab。

### 首页

- 顶部“临期”组最多显示 2 个最紧急食材 +“查看全部”+“用这些做饭”。
- 有待制作菜谱时，显示“待制作 X”和最近加入的 1–2 个菜谱；“今天做什么”保留为次级入口。
- 没有待制作菜谱时，“今天做什么”成为主要入口。
- 库存为空时显示空状态、“添加食材”主按钮和“先看看怎么用”次按钮。

### 库存页

- 默认按食材类别组织，可切换为按保存位置查看。
- 支持搜索、多条件筛选和排序。
- 典型筛选：临期、已开封、冷藏、冷冻、常温。
- 典型排序：最快到期、最近购买、名称。
- MVP 不做批量操作。

## 4. 库存模型与生命周期

### 4.1 两层库存

- **核心食材**：记录批次、数量、日期和保存状态。
- **常备品**：盐、油、香料等只记录“有/无”，参与菜谱缺失判断，不追踪精确数量。

### 4.2 批次

- 同一种食材可有多个批次，分别保存购买日期、数量、保存方式、开封/解冻状态及建议使用日期。
- 重复录入同一种食材时，提示用户选择“新增批次”或“合并到现有批次”，系统不自动合并。
- 仅当购买日期、保存方式、开封状态、解冻状态、包装到期日均一致时，才允许合并。
- 同一批次部分改变保存方式时自动拆分。例如 500g 冷藏鸡胸肉中的 300g 改为冷冻后，形成 200g 冷藏批次和 300g 冷冻批次。
- 后台保留拆分前后的父子关系，前台不展示。
- 多批次扣减默认采用 FEFO：按包装到期日与系统建议使用日期中较早的客观期限排序。

### 4.3 数量与单位

- 固定单位：`g / kg / ml / L / 个 / 份 / 包 / 盒 / 瓶`。
- `g / kg / ml / L` 可用小数；离散单位只允许整数。
- 只自动换算可靠的同类基础单位：`g ↔ kg`、`ml ↔ L`。
- 不估算“个 ↔ g”等跨维度换算。
- 包、盒、瓶可选填包装内数量；填入后可自动拆算、匹配菜谱和扣减。
- 包装被部分消耗后，前台同时保留包装语义与剩余基础数量，例如“1 盒（剩余 10/12 个）”。
- 无可靠换算关系时不猜测，提示用户补充包装内数量。

### 4.4 食材名称

- 后台映射为标准食材实体；前台保留用户输入名称。
- 支持明确同义词、别名、常见缩写和口语名，如“西红柿→番茄”“鸡胸→鸡胸肉”。
- “青菜、肉、鱼”等模糊名称不自动推断，必须让用户选择更具体的食材。

### 4.5 消耗、纠错与移除

- 菜谱制作完成后，系统先给建议扣减量；用户可修改实际食材和实际用量，确认后再扣库存。
- 非菜谱场景支持“用了多少 / 已用完 / 丢弃”快速操作。
- “用了多少”的明细仅后台保留，前台不提供使用历史。
- 数量归零或主动标记“已用完”后，从当前库存移除并保留后台记录。
- “丢弃”从当前库存移除并保留后台丢弃记录。
- “删除”用于纠正错误，需二次确认；采用软删除，前台消失、后台保留最小审计记录，且不计为丢弃或浪费。
- 可单项编辑数量、单位、保存方式、购买日期、包装到期日、开封状态、解冻状态；会影响期限的字段变化后自动重新计算系统建议使用日期。
- MVP 不提供用户可见的“已用完/已丢弃历史”页面。

## 5. 保质期、建议使用日期与提醒规则

### 5.1 两类日期

- **包装到期日**：可选；有明确包装日期时记录。
- **系统建议使用日期**：对有可靠规则的常见食材，由食材类型、保存方式、开封状态、解冻状态等计算；可在没有包装日期时单独存在，也可与包装日期并存。

购买日期默认当天，允许修改。包装日期与系统建议日期同时保留，不互相覆盖。

### 5.2 系统建议日期

- 只对有可靠规则的常见食材自动估算。
- 仅采用官方或公共机构来源；多个来源冲突时取更保守、较短的期限。
- 保存方式、开封或解冻状态改变时自动重新计算。
- 用户只能修改客观状态，不能直接修改系统计算结果。
- 保存前展示建议日期并由用户确认；详情页给出简短依据，并可查看参考来源。
- 非常见食材既无包装日期、又无可靠系统规则时，仍可入库，但明确显示“暂无可靠期限”，不参与临期排序；系统不伪造保质期。

### 5.3 临期提醒与排序

- `expiry_basis_date` 取两个客观日期中较早者；只有一个日期时取该日期，两者都没有时为空。该字段用于 FEFO、临期分级、提醒、推荐排序和超期排除。
- 临期只由 `expiry_basis_date` 分为“正常 / 即将到期 / 今天优先使用”三级。阈值按食材类别给默认值，允许用户在“我的”中调整，不统一写死天数。
- 临期详情按“今天优先使用 → 即将到期 → 正常”排序。
- 已过任一客观期限的食材默认不参与推荐；用户选择“仍保留”后仍不恢复推荐，并明确标记“已过包装/建议日期 · 不参与推荐”。系统不自动删除，仍可由用户手动用完或丢弃。
- 客观事实纠正后若 `expiry_basis_date` 回到未来，系统按新结果恢复推荐资格。
- MVP 的提醒是打开小程序后可见的首页卡片/角标；微信订阅消息放到 V1。

## 6. 菜谱推荐

### 6.1 来源与质量

- 优先检索结构化、可靠菜谱；无法满足约束时再由 AI 生成方案。
- 结构化来源优先官方/专业来源，也可接入经过筛选的大型菜谱平台。
- 入库菜谱至少具备完整的食材、用量、步骤和时间信息，并带菜系、烹饪方式、难度、用时和场景标签。
- 基础字段来自原菜谱，缺失标签可由 AI 补齐，但需规则校验。
- 前台统一显示为“菜谱结果”，不展示“来源菜谱/AI 调整/AI 新方案”等来源标识；后台可保留来源字段用于质量控制。

### 6.2 排序与呈现

- 综合考虑：临期程度、特定类别的已开封状态、实际可用库存、少补买、用户硬约束与软偏好、当前预设模式、时间、难度和厨具。
- 价格与精确补买成本不进入 MVP。
- 默认展示 1 个最佳方案，可展开另外 2 个候选。
- 展示 1–3 条简短推荐依据，不展示评分公式。
- 库存匹配只显示“几乎不用买 / 少量补买 / 需要采购较多”等粗粒度标签，不显示精确百分比。
- 仅显示“高蛋白 / 清淡 / 少油 / 蔬菜丰富”等按规则生成的菜谱特征标签，不展示热量或宏量营养精确值，也不承诺健康效果或摄入达标。

### 6.3 推荐粒度与人数

- “做什么菜”可返回单道菜；“今晚吃什么”返回完整一餐。
- 一餐最多为“主菜 + 配菜 + 主食”三个部分，可包含水果、面包、酸奶、生菜等无需烹饪的部分。
- 用户可明确要求只推荐一道菜。
- 人数改变时，菜谱用量、库存占用、预留和补买清单一起重算。

### 6.4 库存不足、替代与零采购

- 菜谱食材分为“核心必需”和“可选/可省略”。核心缺失进入补买或替代流程；可选缺失不阻塞制作，也不默认要求购买。
- 库存不足时可一键获得替代建议；优先从现有库存与已有常备品中找，并继续遵守过敏、忌口、模式和临时约束。
- 替代只给方案，不自动应用；用户确认后同步更新食材用量、步骤、库存校验和补买清单。
- 份量不足时先建议缩小人数/份量；若用户拒绝，同时提供“补买缺口”和“换一道更匹配库存的菜”。
- 零采购模式是硬约束，只能使用可用库存；无法组成完整一餐时，给当前条件下的最佳可行方案并说明限制，不擅自加入补买项。
- 一般推荐无法满足全部软条件时，直接给最接近的可行方案；过敏、零采购等硬约束不可突破。硬约束彼此冲突且无解时，明确提示无可行方案，并请用户放宽其中一个可覆盖条件。

## 7. AI Agent 范围

### 7.1 入口与交互

- 保留统一 AI Tab 与场景化入口，底层为同一个 Agent。
- AI 首页为“文字聊天 + 快捷任务”；不支持语音输入。
- 固定快捷任务：用临期食材做饭、零采购、15 分钟快手餐；再基于当前库存动态生成 1–2 个建议。
- 从临期卡片、库存或菜谱进入时自动携带当前上下文。
- 只保留当前菜谱这一轮对话上下文；退出或完成后不提供历史聊天列表。

### 7.2 能做什么

- 基于库存推荐单菜或整餐。
- 围绕当前菜谱进行多轮自然语言调整，直到用户确认。
- 可替换核心食材，但每次都必须重算库存和补买清单。
- 调整前展示关键变更，用户确认后才应用；保留上一个完整菜谱版本，支持一次撤销，不保留完整版本链。
- 可回答库存、食材、菜谱、偏好和烹饪问题，也可回答“牛排怎么煎”等泛烹饪问题。
- 烹饪过程中可回答当前步骤问题，并自动带入步骤上下文，但不直接改写后续步骤。
- Agent 对库存、预留和补买清单只有读取与提出方案的权限；用户确认菜谱变更后，由确定性规则派生更新用量、预留和补买清单。
- AI 生成或调整结果在展示前、确认应用前各经过一次确定性校验：过敏、硬忌口、临时排除/必须条件、单位可换算性，以及库存、预留和缺口计算都必须正确。普通模式允许把不足量列为补买缺口；零采购模式才要求现有可用库存足量。校验失败的结果不得标记为可行或写入状态。

### 7.3 不能做什么

- 不作为通用聊天助手。
- 不在 MVP 中通过对话直接新增、扣减或编辑库存，也不直接编辑购物清单。
- 不直接执行收藏、加入待制作或开始烹饪；这些仍由用户通过明确的界面操作触发。
- 不提供医疗营养判断。
- 食品安全只给规则型提示，不判断“闻起来怪、变色后还能不能吃”等具体可食用性问题。

## 8. 偏好与约束

### 8.1 长期设置

- 过敏始终是不可覆盖的硬约束。
- 忌口由用户设为硬约束或软偏好。
- 普通口味偏好只记录“喜欢/不喜欢”，作为排序权重，不设置强度滑杆。
- 支持系统预设饮食模式，如日常、减脂、高蛋白、清淡；这些只是可解释的软排序偏好，不构成健康效果或摄入达标承诺。
- 记录默认人数、可用厨具、可接受时间和难度。
- MVP 不保存长期菜系偏好。

### 8.2 单次临时条件

- 可临时覆盖长期软偏好，但不能覆盖过敏等硬约束。
- 支持临时菜系、口味、烹饪方式、时间、难度、厨具和人数。
- 自然语言区分强度：“只能蒸”为硬约束，“最好蒸”为软偏好。
- 可临时指定一个或多个“本次不要使用”的食材，作为硬约束。
- 可临时指定必须优先使用的具体食材；无法合理放入同一道菜时，优先拆成主菜、配菜或主食，在同一餐尽量使用。
- 可要求必须包含某类食材；“一定要有蔬菜”为硬约束，“想吃点豆制品”为软偏好。

## 9. 购物清单

- MVP 统一称为“菜谱补买清单”。推荐阶段先生成随当前菜谱变化的缺口预览；加入待制作后，该菜谱的补买清单才持久化。多道待制作菜谱分别维护、分别查看，MVP 不合并。
- 自动扣除可用库存，并区分“必须补买 / 可选补买”。
- 可选食材优先提示“可省略/可替代”，默认作为清单外建议，需要时可加入。
- 用户可修改数量或删除条目，但不能手动新增与当前菜谱无关的商品。减少或删除必买项只表示“不购买”，不会改变菜谱需求；菜谱继续标记对应核心缺口。
- 菜谱、替代方案、人数或份量变化后重新校验；先前的手工调整若不再适用则失效，并提示用户复核。
- 常备品缺失只在菜谱中提示，不自动加入补货清单。
- MVP 没有采购回流流程；买到的缺失食材需先手动入库，再由待制作菜谱重新校验。
- 多道待制作菜谱的清单合并、通用购物清单、分批采购、待入库和采购回流库存均放到 V1。

## 10. 待制作与库存预留

- “收藏”和“待制作”是彼此独立的状态，同一道菜可以同时存在于两者中。
- 菜谱加入“待制作”后立即按批次预留库存。
- 新推荐默认不使用已预留库存。
- 修改待制作菜谱后自动重新校验库存，并同步更新预留量与该菜谱的补买清单；支持一次撤销。
- 取消待制作菜谱后立即释放预留。
- 预留只在取消、明确重分配或完成制作时释放/核销，不因时间自动释放；用户可之后补记已制作。
- 用户明确把已预留食材改用于另一道菜时，旧菜谱的预留被取消并退出待制作；前台不建立“未制作”列表，该菜谱以后仍可作为普通候选再次推荐。
- 制作完成时优先核销本菜谱自己的批次预留：少用则释放余量，多用则从未预留库存按 FEFO 补扣；不得静默占用其他菜谱的预留。
- 用户要占用其他菜谱的预留时必须明确确认，并以原子操作完成“新方案可成功预留 → 旧菜谱释放并退出待制作”。任一条件失败则保持原状态。
- 涉及另一道菜的重分配是独立确认事务，不纳入当前菜谱的“一次撤销”；执行前必须提示该影响。
- 制作完成后，预留转为实际扣减，菜谱移出待制作并进入已制作历史；收藏状态不变。

## 11. 烹饪模式

- 进入逐步模式前先显示完整备料清单和必要预处理，不要求逐项勾选。
- 每次只显示当前步骤；支持上一步/下一步自由切换。
- 每一步同时显示操作说明及本步骤食材与用量。
- 支持大字模式和屏幕常亮；暂不支持横屏。
- 可暂停并稍后继续，系统记住当前步骤。
- 退出时不二次阻拦，只提示进度已保存。
- 可随时询问 AI 当前步骤问题，AI 不直接修改后续菜谱。
- 最后一步完成后直接进入“确认实际食材与用量 → 扣减库存”。
- 计时器放到 V1。

## 12. 收藏与已制作历史

- MVP 支持收藏系统推荐菜谱。
- 菜谱详情同时保留“收藏”和“加入待制作”两个独立按钮。
- 收藏列表可直接“加入待制作”，按收藏时间倒序，不做搜索或筛选。
- 收藏保存用户点击时所见菜谱版本的快照；从收藏加入待制作时，按当前库存和硬约束重新校验。
- 已制作历史只保留菜名、制作时间和完成时最终菜谱快照，按制作时间倒序且只读，不做搜索、筛选或“再做”。实际用量另存后台事件，不改写历史菜谱步骤。
- 用户手动创建菜谱、个人副本、标签/备注编辑、完整版本管理、详细制作上下文、反馈学习等放到 V1。
- 前台不提供“未制作”列表；想长期保留的菜谱应使用收藏。

## 13. Onboarding

- 采用渐进式 Onboarding。
- 首次只收集过敏/忌口和默认人数；安全字段保存“有 / 明确无 / 未确认”。未确认时可浏览，但首次生成可执行推荐前必须完成确认。
- 首次进入提示添加第一批食材，但允许跳过。
- 提供使用演示数据的、可跳过的 3 步示例：“添加食材 → 查看临期提醒 → 用现有食材生成菜谱”。
- 演示数据与真实云端库存隔离，不生成真实提醒、预留或历史。
- 未设置饮食模式、厨具、时间或难度时不作为约束；默认只应用已确认的安全约束与默认人数。
- MVP 仅手动入库；不以拍照或 OCR 作为首次使用前提。

## 14. MVP 范围

MVP 必须完整跑通：

1. 微信登录、云端同步与渐进式 Onboarding；
2. 手动录入、编辑、拆分、合并和扣减食材批次，以及常备品“有/无”管理；
3. 常见食材的建议使用日期、临期分级、首页提醒及“用这些做饭”；
4. 基于实际可用库存、预留、偏好和临时条件推荐单菜/整餐；
5. AI 多轮调整当前菜谱，确认后应用并支持一次撤销；
6. 推荐候选的补买预览，以及各待制作实例的必买/可选补买清单与库存替代；
7. 待制作、库存预留、取消/修改及冲突重分配；
8. 逐步烹饪、进度保存、完成时确认实际用量；
9. FEFO 扣减、快速非菜谱扣减、用完/丢弃/软删除；
10. 收藏与基础已制作历史。

## 16. 明确的产品非目标

- 实际摄入、热量、宏量或微量营养追踪；外卖、外食、零食记录。
- 将购买、库存扣减或菜谱用量解释为用户真实摄入。
- 医疗营养诊断、疾病管理、营养处方或“是否摄入达标”判断。
- 根据气味、颜色、口感等远程判断食物是否还能食用。
- 通用聊天助手。
- 自动猜测模糊食材、不可换算单位或缺乏可靠依据的保质期。

多人共享家庭库存与成员级记录不属于 MVP，也尚未承诺进入 V1；当前只做数据结构预留。

## 17. 核心端到端流程

### 17.1 首次使用

微信登录 → 设置过敏/忌口与默认人数 → 可跳过演示和第一批食材录入 → 首页空状态或临期/决策入口。

### 17.2 入库与临期

输入名称、数量、单位、保存方式和日期 → 标准化名称 → 选择新增或合并批次 → 展示系统建议日期 → 用户确认 → 入库 → 计算客观期限 → 首页提示 →“用这些做饭”。

### 17.3 推荐、调整与补买

读取可用库存并排除已预留量 → 合并长期设置与本次条件 → 检索可靠菜谱/必要时 AI 生成 → 返回最佳方案及候选 → 展示已有、替代和补买 → 用户多轮调整 → 展示变更 → 确认最终版。

### 17.4 待制作与预留

加入待制作 → 立即按批次预留 → 修改时重算预留和补买 → 取消时释放；若明确重分配食材，则旧菜谱退出待制作。

### 17.5 烹饪与扣减

备料清单 → 逐步烹饪 → 可暂停/恢复和问 AI → 完成 → 核对实际食材与用量 → 优先核销本菜谱预留、额外数量再按 FEFO 补扣 → 用户确认 → 原子更新预留与库存 → 归零批次进入已用完记录 → 菜谱进入历史。

### 17.6 非菜谱消耗

库存详情 →“用了多少/已用完/丢弃”→ 更新或移除当前库存 → 后台记录事件，前台不展示历史。

## 18. 状态机与关键规则

### 18.1 库存批次状态

```text
草稿
  └─确认入库→ 在库
                  ├─部分消耗→ 在库（更新剩余量）
                  ├─部分改变保存方式→ 原批次减量 + 新子批次
                  ├─数量归零/标记用完→ 已用完（后台）
                  ├─丢弃→ 已丢弃（后台）
                  └─删除→ 软删除（后台审计，不计浪费）
```

开封、解冻、保存方式和购买/包装日期变更属于属性变化，会触发建议日期重算，不是独立终态。“是否超过客观期限/是否可推荐”与上述生命周期正交：批次可仍然在库，但被标记为不可推荐；事实纠正后可重新计算并恢复。

### 18.2 菜谱状态

```text
推荐结果
  ├─收藏↔取消收藏（与其他状态独立）
  └─加入待制作→ 待制作 + 已预留
                    ├─修改→ 重算预留/补买，保留一次撤销
                    ├─取消或食材被明确重分配→ 释放预留并退出待制作
                    └─完成制作→ 确认实际用量→ 实际扣减→ 已制作历史
```

### 18.3 约束优先级

1. 不可突破硬约束：过敏、零采购、用户明确的排除/必须条件。
2. 准确计算可用量（实际库存减去有效预留）和缺口；普通模式可生成补买项，零采购模式必须库存足量。
3. 优先临期和特定类别已开封食材。
4. 尽量满足软偏好、预设模式、时间、难度、厨具与少补买。
5. 无法满足软条件时返回最接近方案；不得静默突破硬约束。

### 18.4 一致性规则

- 任何菜谱食材替换、份量或人数变化，都必须同步重算步骤、用量、库存、预留和补买。
- 任何影响保存期限的库存属性变化，都必须同步重算系统建议日期与提醒。
- 已预留批次的非菜谱变更使用固定规则：不改变数量/身份的属性编辑保留预留；拆分时按客观 FEFO 将原预留迁移到子批次；合并时把各批次预留按待制作实例汇总到新批次。以上均须原子执行并重算期限。
- 若减量、快速消耗、丢弃或删除会使数量低于有效预留，默认阻止操作；用户必须先明确取消或重分配受影响的待制作实例，成功后再原子执行库存变更。系统不得自动取消菜谱或让预留静默失效。
- 属性编辑或时间经过导致已预留批次超过客观期限时，保留预留但把待制作实例标记为“食材期限已变化”；在替换食材、取消菜谱或重新校验通过前，不允许进入系统引导的烹饪流程。
- 完成制作按 `(pending_recipe_id, ingredient_id, batch_id)` 逐行核销：匹配预留先扣，未使用的预留释放；改用其他食材/批次或超出预留的数量，只能从未预留库存按 FEFO 补扣。库存不足时阻止确认并要求补录库存、调整用量或显式重分配，库存不得为负。
- 涉及其他待制作实例的重分配属于独立原子事务；普通菜谱版本撤销不恢复被取消的其他菜谱及其预留。
- 收藏不占库存；只有待制作占用预留。
- `expiry_basis_date` 是 FEFO、临期分级、提醒、推荐排序和超期排除的唯一日期依据。FEFO 排序中，有客观期限的批次优先于无期限批次；同日期时按购买日期、再按入库时间从早到晚排序。

## 19. 重要数据字段与假设

### 用户与偏好

- `user_id / wechat_identity`
- `default_servings`
- `allergies[]`
- `avoidances[]`：含 hard/soft
- `taste_likes[] / taste_dislikes[]`
- `preset_mode`
- `cookware[]`
- `default_time_limit / default_difficulty`
- `expiry_warning_thresholds[]`
- `allergy_profile_state`：has、explicit_none、unconfirmed
- `avoidance_profile_state`：has、explicit_none、unconfirmed

### 标准食材与库存批次

- `ingredient_id / canonical_name / display_name`
- `category`：蔬菜、水果、肉类海鲜、蛋奶、豆制品、主食谷物、其他
- `batch_id / parent_batch_id`
- `quantity / unit`
- `package_quantity / package_base_quantity`（可选）
- `purchase_date`
- `package_expiry_date`（可选）
- `system_use_by_date / rule_version / source_reference`（可选）
- `expiry_basis_date / recommendability`（派生字段）
- `storage_method / opened_state / thawed_state`
- `status / deleted_at / created_at / updated_at`

### 菜谱、清单与预留

- `recipe_id / source_type`（仅后台）
- `title / servings / time / difficulty / cookware[] / tags[]`
- `ingredients[]`：标准食材、数量、单位、required/optional
- `steps[]`
- `temporary_constraints[]`：hard/soft 与当前会话作用域
- `previous_version_snapshot`：仅一次撤销
- `favorite_id / recipe_snapshot / favorited_at`
- `pending_recipe_id / recipe_snapshot / status`
- `reservation_id / pending_recipe_id / batch_id / reserved_quantity / status`：active、consumed、released
- `shopping_item_id / pending_recipe_id / ingredient_id / required_type / required_quantity / available_quantity / buy_quantity / override_type / override_status / substitutes[]`

### 常备品

- `pantry_item_id / ingredient_id / availability`：available、unavailable
- `updated_at`

### 制作与事件

- `cook_record_id / final_recipe_snapshot / cooked_at`
- `actual_usage[]`：批次、实际食材、实际数量
- `inventory_event`：add、edit、consume、used_up、discard、soft_delete、split、merge、reserve、release

### 关键假设

- MVP 只有手动入库，所有入库默认视作一次采购/获得记录，不细分赠送、带回等来源。
- 自动建议日期仅覆盖有官方可靠规则的常见食材。
- 精确库存依赖用户确认；系统不对模糊名称、包装容量或跨维度单位做猜测。
- 推荐中的营养信息仅为菜谱标签和一般搭配规则，不能推导用户实际摄入。
- 菜谱补买清单在推荐阶段是临时预览，加入待制作后才持久化；必买项被手工删除也不会消除菜谱本身的缺口。
- 同一菜谱可多次加入待制作；预留和补买清单始终绑定具体 `pending_recipe_id`，不能只绑定菜谱模板。
- `override_type` 区分改数量/明确不买；重算后不再适用时置为待复核，不能静默沿用。
- 预留与库存扣减需原子更新；失败时回滚，不产生部分扣减或悬空预留。
- 后台应保存规则版本、菜谱快照和库存事件，保证重新计算、纠错与后续 V1 分析可追溯。
